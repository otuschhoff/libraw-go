# Initial ORF layout evidence and algorithm notes

Evidence scope: the four hashed inputs in the
[fixture manifest](../testdata/fixtures.json), LibRaw 0.21.4 at
`9646d776c7c61976080a8f2be67928df0750493e`, and ExifTool 13.40 at
`e2a8542f9c900eae70cb016f0ed410c1bfd4c1ac`.

These are source-informed, LGPL-covered notes, not a clean-room format
specification. "Measured" below means observed in these exact files or
compared against every exported sample. "Reference-derived" describes
behavior read from the pinned implementation, not experimentally established
for every Olympus model. The two implemented layouts have their own primitive,
malformed-input, and full-sample differential tests.

## 1. Container: measured facts

All four inputs start with `49 49 52 4f 08 00 00 00` (`IIRO` followed by a
little-endian first-IFD offset of 8). IFD0 has 21 entries, with little-endian
classic TIFF entry encoding. The TIFF identifier is ORF-specific, not
standard TIFF's 42. This corpus does not evidence `MMOR`, `IIRS`, BigTIFF,
or other header forms; those must remain unsupported initially.

All four IFD0s declare:

- BitsPerSample = 16, Compression = 1, PhotometricInterpretation = 1.
- One sample per pixel, with CFA interpretation supplied separately.
- EXIF CFAPattern and Olympus ValidBits = `12 0`.
- Orientation = 1.

Consequently, neither a nominal 16-bit field, compression 1, nor grayscale
photometric interpretation distinguishes plain words from compressed Bayer.
The public sample archive's "16bit" labels are likewise not decoder selectors.

The IFD0 sensor organization is:

| Fixture ID | Dimensions | Rows/strip | Strips | First offset | Total payload bytes |
|---|---:|---:|---:|---:|---:|
| olympus-e-1-1800 | 2624 x 1966 | 130 | 16 | 344064 | 10317568 |
| olympus-e-400-2151 | 3768 x 2840 | 32 | 89 | 650752 | 21402240 |
| olympus-e-410-1173 | 3720 x 2800 | 2800 | 1 | 655360 | 9632981 |
| olympus-e-510-5449 | 3720 x 2800 | 2800 | 1 | 655360 | 10180944 |

Every strip in each word-based file is physically contiguous with its logical
predecessor. Every complete row is `2 * width` bytes. The last strips contain
16 rows (E-1) and 24 rows (E-400). This proves contiguous, row-major word
reconstruction only for these fixtures; it does not prove arbitrary strip
concatenation or restart behavior for compressed multi-strip ORFs.

Every offset/count, first payload prefix, MakerNote location/header, and byte
order is recorded in its machine-readable `testdata/reference/ID.layout.json`.
Those files are regenerated by an independent bounded IFD evidence scanner.

## 2. MakerNotes: measured facts and bounded compatibility requirements

### Older OLYMP form: E-1 and E-400

Both begin at file offset 788 with `OLYMP\0 02 00`, followed immediately by
the little-endian root directory count 27. The root IFD therefore starts at
MakerNote + 8. Referenced tag data uses file/TIFF-origin offsets, not offsets
relative to the MakerNote header.

In the E-1 sample, root tag `0x2040` is an UNDEFINED byte block of declared
length 1320 at absolute file offset `0x0790`. Its first uint16 is directory
count 110. Root `0x2010` is an UNDEFINED block of declared length 252 at
absolute file offset `0x0466`, containing directory count 21.

These declared subdirectory lengths are **two bytes shorter than the count
field plus their entry arrays**. ExifTool validation reports this known
Olympus encoding quirk, including Equipment, CameraSettings, RawDevelopment,
ImageProcessing, and FocusInfo on E-1. It also reports odd offsets for some
EXIF values. The reference decoder unpacks the image without data errors.

Production parsing must model these old subdirectories deliberately:

- Do not apply a generic "all MakerNote values are contained in the declared
  MakerNote blob" rule. For example, E-1's MakerNote tag declares 3038 bytes,
  but valid referenced calibration data occurs beyond that span.
- Require the needed directory count/entries and each referenced value to
  fit the file, with normal depth/count budgets.
- Recognize the bounded old-directory length quirk explicitly; do not broaden
  this to arbitrary truncated directories or zero-filled missing bytes.
- Do not blindly demand a classic TIFF next-IFD pointer after every
  MakerNote subdirectory; establish the variant's actual framing first.
- Preserve a diagnostic where this compatibility behavior is used.

This distinction belongs in the Phase 2 parser tests. A blanket TIFF
subdirectory implementation that rejects these fixtures is incomplete.

### Newer OLYMPUS form: E-410 and E-510

Both begin at absolute offset 3328 (`0x0d00`) with
`OLYMPUS\0 II 03 00`; the root IFD begins at MakerNote + 12.
Directory offsets are relative to the MakerNote start. In the E-410 file:

- EquipmentIFD `0x2010` has relative offset `0x72`, hence absolute `0x0d72`.
- RawDevelopmentIFD `0x2030` has relative offset `0x3a2`.
- ImageProcessingIFD `0x2040` has relative offset `0x450`, hence absolute
  `0x1150`, where its directory count is 142.

Do not confuse these relative pointers with the old form's out-of-line
UNDEFINED blocks. Byte order must be read from the header rather than
inherited by assumption. Only little-endian instances are measured here.

## 3. Geometry, CFA, and calibration domain

For these four files LibRaw's raw width/height equal the decoded width/height,
the byte pitch is exactly twice width, and native top/left margins are zero.
Both native decoders initialize the full exported plane. Extra allocation
rows and padding are excluded from the oracle.

MakerNote inset crops differ from those native margins:

| Model | Crop `(left,top,width,height)` | Raw-coordinate half-open rectangle |
|---|---|---|
| E-1 | 36,34,2560,1920 | (36,34)-(2596,1954) |
| E-400 | 74,52,3648,2736 | (74,52)-(3722,2788) |
| E-410 | 52,44,3648,2736 | (52,44)-(3700,2780) |
| E-510 | 16,24,3648,2736 | (16,24)-(3664,2760) |

All crop origins happen to be even. That does not justify ignoring CFA phase
for future odd-offset crops. The initial geometric interpretation is an
inset active-area candidate, not an instruction to crop decoded sensor data.
Phase 2 must preserve both geometries and validate each rectangle.

E-1/E-400's raw-origin Bayer cells are G,R / B,G. E-410/E-510's are R,G / G,B.
LibRaw retains separate greens with indices `RGBG`; the exported cells are
respectively `[1,0,2,3]` and `[0,1,3,2]`. EXIF CFAPattern independently agrees.
No rotation is applied; native flip 0 corresponds to observed EXIF orientation 1.

Measured sensor ranges and native calibration:

| Model | Sample min/max | Native scalar black | Native white maximum |
|---|---|---:|---:|
| E-1 | 69 / 4095 | 65 | 4095 |
| E-400 | 81 / 4095 | 95 | 4095 |
| E-410 | 71 / 3418 | 73 | 3946 |
| E-510 | 52 / 2929 | 73 | 3946 |

Below-black samples are legitimate unprocessed observations, not corruption.
The white maximum is not always 4095. Camera-table maximum/matrices are
reference-derived calibration, not proof of per-file tag provenance.
Rendering and profile selection remain Phase 6 work.

## 4. Layout `olympus-word16le-high12`

### Selection scope

Candidate inputs match the measured IIRO/old-MakerNote form, camera identity,
16-bit storage / 12 valid bits, contiguous row-sized strip organization,
EXIF Bayer pattern, and exact two-byte-per-sample payload length.
Only E-1 and E-400 fixture combinations have been measured.

These predicates identify this initial family; payload size alone must not
classify an unknown camera or mode. Phase 3 implements the
[selector](../plan.go) and [word decoder](../word.go) with exact sample tests.
Present TIFF FillOrder, PlanarConfiguration, Predictor, SampleFormat and
ImageDepth controls must be correctly typed scalar values of one; other
encodings remain unsupported rather than being ignored during word decoding.

### Measured storage conversion

Read each word little-endian, then perform an unsigned right shift by four.
The resulting uint16 is the sensor-code value. Do not mask with `0x0fff`
without shifting and do not scale back into a 16-bit output range.

This equation was independently compared against **all 15,859,904 samples**
across E-1 and E-400: zero mismatches.

The E-1 payload has no nonzero low nibbles. The E-400 payload has **793**
nonzero low nibbles; the reference discards them. Rejecting such words would
break a real approved fixture. Their physical meaning is not established.
No extra row shuffle or predictor is required for these two files.

### Reference-derived behavior

Relevant pinned symbols:

- `LibRaw::unpacked_load_raw`, `src/decoders/generic.cpp`.
- Olympus adjustment in `identify_finetune_dcr`, `src/metadata/identify.cpp`.
- TIFF raw-layout dispatch in `src/metadata/tiff.cpp`.

The final Olympus load flags select the four-bit shift. Other Olympus modes
can select different shifts, packing, or byte orders; do not generalize this
routine to them.

### Primitive test vectors for Phase 3

| Stored bytes | Little-endian word | Sensor code after shift |
|---|---:|---:|
| `00 00` | 0x0000 | 0 |
| `10 00` | 0x0010 | 1 |
| `3f 12` | 0x123f | 291 |
| `f0 ff` | 0xfff0 | 4095 |
| `ff ff` | 0xffff | 4095 |

Add alternating maximum/zero patterns across row and strip boundaries,
the 16-/24-row final strips, truncated words/arrays, and contradictory sizes.
Big-endian and interleaved packing need separate evidence and selectors.

## 5. Layout `olympus-legacy-predictive12`

### Measured framing

Both initial compressed files have one strip at 655360, 3720 x 2800 stored
samples, ValidBits 12, and the newer MakerNote form. The strip's first seven
bytes are `00 00 00 00 01 00 00`. The payload after those bytes is not a
word array and is not a JPEG stream.

LibRaw successfully exports 10,416,000 samples from each file, without data
errors or processing warnings. The two output SHA-256 values differ and are
recorded in the index. The bitstream uses MSB-first consumption independent
of the enclosing TIFF's little-endian scalar byte order.

### Reference-derived entropy/state rules

Relevant symbols: `LibRaw::olympus_load_raw` and `LibRaw::getbithuff`,
`src/decoders/decoders_dcraw.cpp`, plus TIFF dispatch and Olympus
identification adjustments. The production implementation must explicitly
bound all widths, loops, arithmetic, input extents, and reconstructed values.

The algorithm can be specified without reproducing the native source:

1. Skip the seven-byte prefix. The reference does not validate its contents;
   the initial production plan should recognize the evidenced prefix and
   reject unfamiliar framing as unsupported rather than guess.
2. Reset bit-reader state once per image. Two independent adaptive contexts,
   selected by column parity, reset to three zero integers at each row.
3. Each context holds the previous unsigned residual magnitude, a signed
   residual-bias accumulator, and a count of small residuals.
4. If the count is below three, set auxiliary `i=2`; otherwise `i=0`.
   Begin residual suffix width at `2+i`, increasing it while the previous
   magnitude, interpreted as uint16, shifted right by `(width+i)` is nonzero.
5. Consume three bits: their top bit selects sign and their bottom two bits
   are the reconstructed sample's low bits.
6. Decode a prefix: `k` leading zeroes followed by one represents high value
   `k`, for `0 <= k <= 11`. Twelve zeroes are the escape marker.
7. An escape consumes **16 minus suffix-width bits**, then shifts that
   entire extracted number right by one to obtain the high value. The
   discarded bit must still be consumed.
8. Read suffix-width bits. Magnitude is `(high << suffix-width) + suffix`.
   Positive sign contributes magnitude; negative sign contributes its
   bitwise complement, i.e. `-magnitude-1`, not simply `-magnitude`.
9. Add the previous signed bias to obtain the residual. Update bias to the
   arithmetic-right-shift-by-five of `(3 * residual + old bias)`.
   Reset the small-residual count to zero when magnitude exceeds 16;
   otherwise increment it.
10. Decode all coded columns, including any beyond the useful output width;
    state consumption cannot stop at the crop boundary.
11. Add the predictor to the signed residual shifted left by two, combined
    with the two low bits. Require the reconstructed sample in 0..4095.

The prefix table in LibRaw is a speed optimization, not a requirement for a
Go lookup table. A bounded bit-at-a-time prefix parser may avoid speculative
lookahead. Never imitate an out-of-input read or silently supply zero bits.
No byte-stuffing interpretation is evidenced for these ORFs; the exported
native `zero_after_ff` value records the actual reference setting.

### Reference-derived prediction

Neighbors are two raw pixels apart, i.e. same-CFA-position values:

- In the first two rows and first two columns: predictor zero.
- In the first two rows only: use west at `(x-2,y)`.
- In the first two columns only: use north at `(x,y-2)`.
- Otherwise name west `w`, north `n`, and northwest `nw`.
- If `nw` lies strictly between `w` and `n`, use `w+n-nw` when either absolute
  difference from `nw` is greater than 32; otherwise use integer `(w+n)/2`.
- Outside that strict-between branch, select `w` if its absolute difference
  from `nw` is greater than `n`'s; otherwise select `n`. Ties select north.

### Phase 4 implementation contract

The pinned decoder source and archive hashes were reverified before
implementation. The following choices freeze the initial Go algorithm:

- The previous magnitude is retained in full for residual arithmetic, but
  **only its low 16 bits** participate in suffix-width selection, matching
  the reference's explicit unsigned-short conversion. Widths are 2..16.
- Residuals, bias, and predictors use signed 32-bit arithmetic. Negative
  right shifts are arithmetic in Go; reconstruction uses `4*residual+low`
  rather than depending on a C signed left shift. The maximum coded
  magnitude is 786431, so these operations cannot overflow int32.
- The small-residual count saturates at three: only the predicate `< 3`
  affects decoding. Both parity contexts reset at every row.
- A fixed 4096-byte input buffer and the full output plane suffice; no
  compressed-payload copy or extra predictor rows are needed. Bit fields
  consume exactly their required MSB-first bits, with no Huffman lookahead,
  byte stuffing, zero filling, or speculative EOF requirement.
- All coded columns consume residuals, including columns outside an output
  rectangle. The current public selector evidences only equal coded/output
  widths, and always retains the entire stored sensor plane; an active crop
  does not alter either width.
- After the final coded sample, unused bits in the last byte and any
  remaining declared strip bytes are opaque trailing data, not required
  field bits. Their values are not constrained or scanned. This permits
  exactly exhausted streams and never extends a read past the declared
  strip. The input-size quota still bounds the declared extent.

Measured Phase 4 consumption:

| Fixture | Coded bits after header | Required strip bytes including header | Unused final bits | Whole trailing bytes |
|---|---:|---:|---:|---:|
| olympus-e-410-1173 | 77063789 | 9632981 | 3 | 0 |
| olympus-e-510-5449 | 81447495 | 10180944 | 1 | 0 |

Both entire planes match the pinned sample hashes. Tests decode with exactly
these byte extents and reject removal of the final byte even though the source
still physically contains it. Synthetic streams additionally test arbitrary
unused-bit values and declared trailing bytes; neither is a required lookahead.

The physical meaning of the seven-byte header and the full universe of
trailing-padding patterns are not established by this corpus. No universal
claim is made. The observed header is validated by the layout selector;
other headers remain unsupported. Required field bits cannot be replaced
by padding or by bytes physically following the declared strip.

No evidence here supports compressed multi-strip restart rules, alternative
predictor thresholds, non-12-bit output, or newer parameterized compression.
Those are outside the initial selector.

## 6. Capture modes and support boundary

The E-410 file has DriveMode `1 1 0` and SpecialMode `2 1 0`; this is
burst/panorama-sequence metadata. It still stores one Bayer frame. Do not
equate sequence membership with multi-frame reconstruction, and do not
erase those mode values from future support claims. The other three files
have the zero SpecialMode values shown in the manifest.

Software tags are `Version 1.1` on E-1/E-400 and `Version 1.3` on E-410/E-510.
These strings are retained; independently verified firmware identifiers are
unknown. No high-resolution/pixel-shift or ORI input is included.

There are two distinct real files per measured layout but only one per
camera/mode. Phase 0 therefore establishes initial layout evidence, not the
design's production camera-certification gate. Phases 3-4 implement the
evidenced word and legacy predictive layouts with exact full-plane parity.

## 7. Embedded JPEG evidence (Phase 2)

The Olympus CameraSettings directory contains `PreviewImageValid` (`0x0100`,
LONG), `PreviewImageStart` (`0x0101`, LONG), and `PreviewImageLength` (`0x0102`,
LONG). A valid flag of one enables the start/length pair. Old OLYMP starts are
file-relative; new OLYMPUS starts are MakerNote-relative. For example, E-410
stores 21248, resolved against MakerNote base 3328 to absolute byte 24576.
ExifTool's normalized PreviewImageStart in the frozen reference JSON is already
absolute; production parsing must not add the base a second time.

The production integration gate independently reads the reference-selected file
range and compares every extracted JPEG byte:

| Fixture | Absolute start | Bytes | JPEG dimensions | SHA-256 |
|---|---:|---:|---:|---|
| olympus-e-1-1800 | 34156 | 291265 | 1280 x 960 | `2b24d47b4763a8556d5b8014e96031ea95242e6a5f316a35a6f64524f4411865` |
| olympus-e-400-2151 | 24576 | 308009 | 1600 x 1200 | `b5076607e9c75e2db4095f8892e72fc599caf8499f6b05df086a00db3cf21890` |
| olympus-e-410-1173 | 24576 | 388113 | 1600 x 1200 | `b39a567cf8ee06b64811eb4c6c64e08f8c391f5317716480ff0fa8d0f5cb4079` |
| olympus-e-510-5449 | 24576 | 422737 | 1600 x 1200 | `3da97b5824419f4ddf4d73df303cb0a4f2cec3de8c98e9a51fd1bf253866b87d` |

E-1/E-400 also contain smaller TIFF IFD1 JPEGs. TIFF JPEG offsets use the
file origin, not the MakerNote base. Supported candidates are selected by
descending pixel area, descending byte length, then ascending absolute offset.
Opening validates extents, SOI/terminal EOI, supported JPEG frame headers and
configured limits without decoding entropy/pixels. Preview extraction returns
the original bytes separately, never a raw fallback.

The four Olympus CameraSettings previews have no independently verified
orientation-to-display transform. The sensor EXIF orientation is not proof of
their encoded-pixel orientation. Production therefore leaves that preview
orientation unavailable and reports a diagnostic. When a TIFF preview IFD
provides its own EXIF orientation, that value is preserved unchanged.
